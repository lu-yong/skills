本文件只摘录“处理任务要求”和相关标签定义中与本 skill 直接相关的规则，不替代完整 wiki。遇到本文件未覆盖的情形，以在线 wiki 为准。

## 跟踪类型与字段矩阵

`结论`是本 skill 的核心字段，对所有跟踪类型都需要在草稿中填写和确认。除此之外，根据 issue 的精确跟踪类型填写以下字段：

| 跟踪类型 | 需要填写的字段 |
| --- | --- |
| `功能` | `状态`、`接口调整`、`%完成` |
| `错误` | `状态`、`接口调整`、`%完成`、`问题性质`、`问题归属`、`公版问题类别` |
| `节点` | `状态`、`%完成` |
| `需求` | `状态` |
| `测试` | `状态`、`%完成` |

使用 Redmine 返回的 `issue.tracker.name` 做匹配。未列入矩阵的字段不应因为已有值就被自动修改；跟踪类型缺失或不在矩阵中时，先询问用户。

## 普通结论

任务处理完成、状态变更前，结论必须言简意赅并包含三个要素：

```text
问题原因：
处理方案：
影响范围：
```

有代码补丁时，处理方案应说明实际修改内容，并记录 Gerrit 补丁号。

## 状态与完成度

- 开始处理任务时，状态应从 `新建` 修改为 `已确认`。
- 只有在任务处理完成、结论完整、相关字段准确，并满足补丁评审/测试前置条件时，才可将状态改为 `已解决`。这四项前置条件由用户保证，不通过 Gerrit、Git 或测试证据检测；在拟改为 `已解决` 前，必须要求用户按以下格式确认：
  ```text
  提交前自测：已完成/未完成
  干净版本补丁测试：已完成/未完成
  提交者自 Review+1：已完成/未完成
  依赖补丁：无/有，且已合入 sdk-release/有但未合入
  ```
  仅当前三项均为 `已完成`，且依赖补丁为 `无` 或 `有，且已合入 sdk-release` 时，才允许使用 `已解决`。收到确认后不再要求测试输出、Review 标签或依赖合入证据。
- `已拒绝` 必须有明确拒绝理由，并征得软件版本管理员同意。
- `反馈` 必须说明分析流程结论，并征得任务创建者同意。
- 状态名称和 ID 以 Redmine 返回的实际状态列表或 issue 的允许状态为准；无法判断目标状态时先询问用户。
- `%完成`使用 Redmine 标准字段 `done_ratio`，必须是 0 到 100 的整数；不在矩阵中的跟踪类型不修改该字段。

## 问题性质

常用值及含义：

- `上个版本修改引入`：上个发布版本修改一个问题后引入另一个问题，或上个版本修改不彻底。
- `当前版本修改引入`：当前版本开发修改引入问题、修改不彻底，或当前版本新功能专项测试问题。
- `历史遗留`：从更早版本持续存在到现在的问题。

该字段只对 `错误` 跟踪类型进入更新矩阵。无法从 issue 描述、版本信息和提交证据判断版本关系时，询问用户并使用 Redmine 中的精确选项值。

## 问题归属

- `应用`：基于 GoXceed 平台开发、由应用独立维护的代码功能问题。
- `平台`：纳入 GoXceed 平台驱动框架管理的模块问题。
- `芯片`：芯片本身问题。

该字段只对 `错误` 跟踪类型进入更新矩阵。如果修改内容跨越多个边界，或者代码证据不足以确定维护归属，询问用户。

## 接口调整

该字段在 `功能` 和 `错误` 跟踪类型进入更新矩阵。它借用了“接口调整”标签，实际包括软件接口变更和方案规格变更，例如更换背景图片或增加新功能。根据 issue、提交 diff 和需求描述判断；Redmine 字段的具体选项以 API 返回值为准。无法确认时询问用户。

## 公版问题类别

该字段只对 `错误` 跟踪类型进入更新矩阵，必须使用 Redmine 项目中已有的精确选项值。判断依据包括 issue 现象、涉及模块和提交修改内容。典型类别包括 `代码逻辑`、`设备驱动`、`系统`、`系统性能`、`信道`、`外围环境`、`UI`、`USB`、`网络设置`、`网络APP`、`数据库`、`软件升级`、`Tools`、`DVB`、`EPG`、`PVR`、`Player`、`CA` 等。多个类别都合理且无法唯一确定时，列出候选并询问用户，不自行选择。

## 按问题性质补充

### 当前版本修改引入、上个版本修改引入

对 `错误` 跟踪类型的上述问题性质，结论还必须说明补丁引入关系，并使用以下结构：

```text
问题描述（需求规格）：可选；原任务描述清晰时可以省略。
问题原因：由 {{patch(<Gerrit change number>)}} 修改引入。
处理方案：
影响范围：
修改补丁：{{patch(<Gerrit change number>)}}
```

其中 `<Gerrit change number>` 必须使用已通过 Gerrit 查询核实的数字 change number，不使用未经核实的 Change-Id 或本地 Git SHA 代替。

### 规格变更

除基本三要素外，需要记录：

1. 规格变更原因；
2. 变更前后的差异；
3. 变更前后的使用差异示例；
4. 变更后可能影响的方案项目、功能模块、软件系统或芯片型号；
5. 相关修改补丁（如果有）。

### 已拒绝

明确说明拒绝理由，并确认已征得软件版本管理员同意。该事实无法从代码或 Gerrit 推断时，先询问用户。

### 反馈

说明完整的分析流程和结论，并确认已征得任务创建者同意。该事实无法从代码或 Gerrit 推断时，先询问用户。

## 补丁与范围检查

- 通用需求和通用问题原则上需要考虑是否同步到公版主线；无法确认时询问公版负责人或用户。
- 状态改为 `已解决` 时，须取得用户对提交前自测、干净版本补丁测试、提交者自 Review+1、依赖补丁状态的四行确认；这些内容由用户保证，不要求通过 Gerrit 或测试证据再次核实。
- 非主线补丁在任务状态改为 `已解决` 前，需要确认补丁状态为 `abandoned`。
- 本 skill 会根据跟踪类型更新对应的状态、元数据字段和结论；不会自动修改该跟踪类型未要求的字段或其他 unrelated 字段。
- 草稿应如实报告已核实的分支和补丁信息；四项 `已解决` 前置条件使用用户提供的四行确认，不推断或补齐未确认的值。

## 缓存与刷新

正常执行优先使用本地规则。刷新在线 wiki 的条件：

- 本文件不存在；
- 本文件距上次核对已超过 30 天；
- 用户明确要求刷新规则，或告知规则已变更；
- issue 属于本文件未覆盖的特殊性质或流程。

刷新成功后，更新本文件中的 wiki version 和规则内容。刷新失败但本文件存在时，可以使用本地规则继续生成草稿，但必须明确告知用户使用的是缓存规则；刷新失败且本文件不存在时，停止并请求用户提供规则文本。
